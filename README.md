# CNAP Evaluation and Reporting Platform

> New session or new account? Read `docs/handoff.md` first: it carries everything a milestone needs.


A relational web application for the Center for Cognitive and Neurobiological Approaches to Plasticity (CNAP) at Kansas State University: configurable, versioned surveys and reports; people with CNAP relationships who receive assignments; and persistent research-outcome records (publications, presentations, grants) with their own lifecycle. It replaces workflows currently handled in Piestar.

**Status: Build 1, Milestone 1 complete** — scaffold, database with every integrity rule, local authentication, roles, audit log, administration screens. Milestones 2–9 follow the plan in the Architecture Review.

This README is written for whoever inherits the project. If you can read Python and run two commands, you can run and maintain this application.

## 1. What you need

- Docker and Docker Compose (the normal way to run it), **or** Python 3.12+ and a PostgreSQL 16 server (for development without Docker).
- Nothing else. There is no JavaScript build step and no external service.

PostgreSQL is required even for tests. The rules that protect CNAP data (composite foreign keys, exclusion constraints, `NULLS NOT DISTINCT` unique constraints, a trigger) only exist in PostgreSQL; SQLite is never used.

## 2. First run (Docker)

```bash
cp .env.example .env            # then edit SECRET_KEY at least
make up                         # starts PostgreSQL and the web app, applies migrations
make seed                       # roles, cores, resources, relationship types, scales, pathways
make superuser                  # the first administrator account
```

Open http://localhost:8000/ and log in. The administration area is at `/admin/`.

`make help` lists every command (migrate, test, lint, backup, restore, logs).

## 3. First run (without Docker)

```bash
pip install -e ".[dev]"
cp .env.example .env            # set DATABASE_URL to your PostgreSQL, e.g. postgres://user:pass@localhost:5432/cnap
python manage.py migrate
python manage.py seed
python manage.py createsuperuser
python manage.py runserver
```

## 4. Environment variables

Every variable the application reads is listed and explained in `.env.example`. Settings live in `config/settings/`: `base.py` (everything), `dev.py`, `prod.py`, `test.py` change only what differs.

## 6. The schema is the migrations

`python manage.py migrate` builds the whole database. Two kinds of migration exist:

- `0001_initial.py` in each app: generated by Django from the models (tables, CHECK and UNIQUE constraints, indexes).
- `0002_constraints.py` in `people`, `forms_engine` and `reporting`: hand-written SQL for what Django cannot express — composite foreign keys that keep copied columns truthful, the exclusion constraints, the `project_people` / `core_people` views, the trigger that freezes answered options. Each file explains, in its docstring, which review section requires it.

After changing a model: `python manage.py makemigrations`, read the generated file, run the tests. `tests/test_migrations.py` fails if models and migrations disagree.

## 7. Tests

```bash
make test                       # inside Docker
pytest                          # locally, against DATABASE_URL in .env
```

The suite creates a throwaway test database, applies every migration, and for each rule in the Architecture Review inserts the invalid row and expects PostgreSQL to refuse it. `tests/conftest.py` holds the fictional Dr. Okafor used throughout the review.

## 8. Daily operations

| Task | How |
| --- | --- |
| Back up the database | `make backup` → `backups/<timestamp>.sql.gz`. Copy that file somewhere safe nightly (cron on the host). |
| Restore | `make restore FILE=backups/<timestamp>.sql.gz` |
| Upgrade the application | `git pull`, `docker compose build`, `make up` (migrations run on start), `make test` |
| Add an administrator | Admin → Users → add; give the Administrator role under User roles |
| Grant confidential mentoring access | Admin → Users → the user → User permissions → add `reporting | response | Can view individual mentor and mentee responses…`. Roles never carry it; superuser status does not imply it. The grant is audited. |
| See what happened | Admin → Audit log |

## 9. Accounts and permissions

- Every person has a **Person** record; only people who log in have a **User**, and a user always belongs to one person.
- **Application roles** (Administrator, Evaluation / Reporting Staff, Standard User, Reviewer) are bundles of permissions. `manage.py seed` creates them and sets their permissions; an administrator may adjust them.
- **CNAP relationships** (Core Director, Pilot Mentor, …) are recorded on the person and never grant application permissions.
- `view_confidential_mentoring_data` is a permission granted to named users only.
- Build 1 uses local passwords. K-State single sign-on is configured later without changing anything else; see `docs/sso.md`.
